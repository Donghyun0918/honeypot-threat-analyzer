### 1. 🐛 dev-backend 무한 재시작 — postgres 만 restart 정책이 없었다

`Unable to determine Dialect without JDBC metadata` 로 재시작 루프. 원인은
`dev-postgres` 가 18시간째 죽어 있던 것이고, 그게 안 돌아온 이유는 compose
10개 서비스 중 **postgres 에만 `restart` 가 빠져 있어서** 였다. Docker/WSL 이
내려가면 backend 는 `unless-stopped` 로 돌아오는데 postgres 는 안 돌아오고,
`depends_on` 은 최초 `up` 에만 적용되므로 DB 없이 기동한다.

`restart: unless-stopped` 추가. `/api/health` 200, 10/10 기동 복구.

### 2. 교차검증 모델을 v4 → v5 로 교체

09-14 에 실 ES 문서 250k행으로 학습한 v5 가 `work-real/` 에 만들어져만 있고
승격되지 않은 상태였다. `MODEL_DIR` 은 `models/` 를 보므로 운영은 v4 였다.

핵심은 `classify.py` 에서 **모델이 이미 라벨을 뒤집지 못한다**는 것이다
(`ml_label_raw`/`ml_dissent` 로 교차검증만 한다). 그래서 실제 선택지는
"모델을 켜냐 마냐"가 아니라 **어느 모델로 교차검증하느냐** 였고, v4 로 두면
검토 큐가 모델 쪽 오답으로 채워진다.

`models/` 를 v5 로 교체, v4 는 `models/superseded-v4-csv-sessionjoin/` 에
사유와 함께 보존.

### 3. 🐛 재분류가 애초에 불가능한 구조였다 — `_op_type: "create"`

전량 재분류를 하려고 커서를 지우려다 발견했다. `_build_action` 이
`_op_type="create"` + `_id=원본 문서 _id` 였다. 기존 문서가 전부 있으므로
**100만 건이 version_conflict 로 거부되고 `ml_label_raw` 는 옛 모델 값으로
남는다** — 모델을 바꿔도 재분류라는 동작 자체가 성립하지 않았다.

`index`(덮어쓰기)로 바꿨다. `_id` 가 결정론적이라 재실행은 멱등하다.

같이 고친 것: 배치가 가득 차면(=백로그 잔존) `POLL_INTERVAL` 을 건너뛰고
바로 다음 배치를 돌게 했다. 그전엔 100만 건에 1,029배치 × 30초 = **8.6시간**
이었다. 실제 소요 **약 20분**.

> 도중에 배치당 0.7초 → 11초로 느려졌는데 ES 는 CPU 1% 로 놀고 있었다.
> 범인은 `dev-ollama`(232% CPU · 5.5GB)와의 CPU 경합이었다. LLM 사이드카를
> 잠시 내리고 끝낸 뒤 복구했다. 7.8GB 단일 호스트에서 LLM 과 대량 색인은

### 6. 위 "다음 작업" 3건 — 같은 날 전부 처리

**1. `build_dataset.py --encoders-in` 추가.** 기존 인코더를 그대로 쓰고

옛 `holdout.csv`·`enc_holdout.json` 은 같은 함정이라 교체했다.

**2. 🐛 404 만의 문제가 아니었다 — Spring MVC 표준 예외가 전부 500 이었다.**
`@ExceptionHandler(Exception.class)` 캐치올 때문이다.
`ExceptionHandlerExceptionResolver` 가 `DefaultHandlerExceptionResolver` 보다
먼저 돌기 때문에, 여기서 가로채면 Spring 의 기본 상태 코드 매핑이 아예
실행되지 않는다. 표준 예외는 `ErrorResponse` 를 구현해 자기 상태 코드를
들고 오는데 그게 전부 무시됐다.

캐치올에서 `ErrorResponse` 면 그 상태 코드를 쓰도록 했다. 예외 메시지는 그대로
흘리지 않고(내부 경로가 드러난다) 상태별 한국어 문구로 바꾼다. 4xx 는
`log.warn` 까지만 — 진짜 장애 로그를 오염시키지 않는다.

```
GET  /api/threat-console/summary  500 → 404 "요청한 경로를 찾을 수 없습니다."
POST /api/overview                500 → 405 "허용되지 않은 요청 방식입니다."
POST /api/users/login (CT 없음)   500 → 415 "지원하지 않는 요청 형식입니다."
회귀: overview·ml-stats·llm-stats 200 · 토큰 없으면 403 유지
```

**3. `profiling-service/` 는 의도된 잔재가 아니라 덜 끝난 삭제였다.**
compose 주석은 이미 "같은 이름의 디렉토리가 있었지만 아무것도 참조하지 않아
삭제했다" 고 적고 있었는데, 실제로는 Spring Initializr 기본 `HELP.md`

### 7. compose 서비스명 `profiling-service` → `backend`

6-3 에서 빈 디렉토리를 치우고 나니 서비스명만 옛 이름으로 남았다. 통합 전
별도 서비스였던 시절의 잔재이고, 실체는 `./backend/honeypot` 을 빌드하는
Spring 백엔드다(컨테이너 이름은 이미 `dev-backend` 였다).

**서비스명은 컨테이너 간 DNS 이름이기도 하다** — 프론트 API 라우트 5개가
`SPRING_API_URL=http://<서비스명>:8080` 으로 백엔드에 붙는다. 이름이 곧
주소이므로 실체와 맞춰뒀다.

고친 곳은 `capstone-dev` 안에서 5줄뿐이다:

```
docker-compose.yml:76   profiling-service:            → backend:
docker-compose.yml:256  depends_on: profiling-service → backend
docker-compose.yml:271  SPRING_API_URL: http://profiling-service:8080 → http://backend:8080
setup.sh:127            docker compose logs profiling-service → backend
docker-compose.yml:70~  주석 갱신 (왜 바꿨는지)
```

프론트 코드는 환경변수만 읽으므로 수정 불필요. 이 문서 아래쪽의 옛 기록에
남은 `profiling-service` 언급은 그때의 사실이라 그대로 둔다.

> 서비스명을 바꾸면 기존 컨테이너가 orphan 이 되어 `container_name: dev-backend`
> 가 충돌한다. `docker compose rm -sf profiling-service` 로 먼저 내리고 바꾼 뒤
> `up -d --remove-orphans` 로 올렸다. `SPRING_API_URL` 이 바뀌므로 프론트도
> 재생성된다.

검증:
```

dev-frontend 안에서      SPRING_API_URL=http://backend:8080 → "backend is running"
진입점                   8002 / /dashboard / /tpot-map/ / 8091 health 전부 200
프론트 경유 로그인       토큰 141자 · overview·ml-stats·attacks·model 전부 200
```

### 9. setup.sh 5단계 — 크기 문구를 모델에서 끌어오고, 보유 판정 버그도 고침

**9-1. "약 2GB" 고정 문구.** `.env` 의 `LLM_MODEL` 이 무엇이든 2GB 라고 했다.
실제로는 `exaone3.5:7.8b` 4.8GB 를 받는다 — 새로 받는 사람은 2GB 만 예상하고
기다린다.

태그의 파라미터 수에서 어림한다. ollama 기본 양자화(Q4)가 1B 당 약 0.6GB 다:

```
exaone3.5:7.8b → 약 4.7GB  (실측 4.8GB)
qwen2.5:3b     → 약 1.8GB  (공개값 1.9GB)
llama3.1:8b    → 약 4.8GB
mistral:latest → 크기 언급 생략   ← 태그에서 못 읽으면 아예 말하지 않는다
```

틀린 숫자보다 안 말하는 게 낫다는 원칙으로, 파싱 실패 시 크기를 생략한다.
내려받은 뒤에는 `ollama list` 의 **실제 크기**를 찍는다(`준비됨 (4.8 GB)`).

**9-2. 🐛 보유 판정이 부분 일치였다.** `grep -q "${model%%:*}"` — 태그를 떼고
이름만 봤다. `exaone3.5:7.8b` 가 있으면 `exaone3.5:3b` 를 요청해도 "준비됨"
으로 통과하고, 없는 모델로 llm-analyzer 가 돌다 실패한다.

```
보유: exaone3.5:7.8b 만 있음 · 요청: exaone3.5:3b
  옛 방식 grep -q 'exaone3.5'        → 준비됨(오판 — 받지 않음)
  새 방식 grep -Fxq 'exaone3.5:3b'   → 다운로드 진행(정답)
```

이름+태그를 정확히 맞추도록 `awk '{print $1}' | grep -Fxq "$model"` 로 바꿨다.

검증: `./setup.sh --no-seed` 로 5단계만 재실행 → `✓ exaone3.5:7.8b 준비됨`.
스택 10/10 · `/api/overview` 이벤트 1,027,042 유지.

### 11. 그 과정에서 나온 결함 2건 — 둘 다 수정

**11-1. 🐛 `/api/internal/attack-log` 에 입력 검증이 없었다.**

검증 전에 **사용자 행 INSERT 를 먼저 시도**한다 — `null@honeypot.local` ·
name=null 로 들어가다 not-null 제약에 걸린 것이다. 롤백돼 흔적은 안 남았지만,
형식만 맞으면 계정이 자동 생성되는 경로에 검증이 없다는 뜻이다.

토큰 확인 **뒤에** `username` · `attackType` · `ipAddress` 를 명시적으로 검증해
400 과 빠진 항목 이름을 돌려준다(`payload` 는 선택 — 스캔은 페이로드가 없다).

> `@Valid` 를 쓰지 않았다. 인자 바인딩 단계에서 돌기 때문에 **토큰 검사보다
> 먼저** 실행되고, 그러면 틀린 토큰으로도 400 이 나가 본문 스키마를 떠볼 수
> 있다. 인증이 먼저다.

```
빈 본문 {}                 400 "필수 항목이 비어 있습니다: username, attackType, ipAddress"
username 만 있음           400 "필수 항목이 비어 있습니다: attackType, ipAddress"
공백 문자열                400 "필수 항목이 비어 있습니다: username"
정상 요청                  200 {"id":1,"attackType":"Recon",…}
틀린 토큰 + 빈 본문        403 Invalid service token   ← 400 보다 우선
```

검증용으로 임시 토큰을 넣고 시험한 뒤 `.env` 를 되돌렸고(현재는 키가 없어
fail-closed, 임의 토큰 403), 테스트가 만든 `sensor1@honeypot.local` 계정·
프로젝트·로그도 지웠다(users 는 demo 하나만 남음).

**11-2. 🔒 `.env.bak-*` 가 gitignore 대상이 아니었다.**
`.gitignore` 의 `*.env` 는 `.env` 만 잡고 `.env.bak-20260914-190546` 같은
이름은 안 잡혀 `git status` 에 `??` 로 올라왔다. 그 파일에 `JWT_SECRET` 이

### 17. `open-in-view` 를 끄려다 나온 것 — `@Transactional` 이 한 군데도 없었다

기동마다 뜨던 `spring.jpa.open-in-view is enabled by default` 경고를 없애려고
설정을 보다가, **그냥 끄면 `/api/projects` 가 깨진다**는 걸 먼저 확인했다.

`ProjectResponse` 가 `project.getUser().getEmail()` 을 읽는데 `Project.user` 는
`FetchType.LAZY` 다. 그런데 코드베이스에 `@Transactional` 이 **하나도 없었다** —
리포지토리 호출이 끝나면 엔티티가 분리되므로, DTO 를 만들 때 지연 로딩이
터져야 정상이다. 지금까지 동작한 건 순전히 **open-in-view 가 영속성 컨텍스트를
요청 끝까지 열어두었기 때문**이다. 우연히 맞아 있던 셈이다.

`ProjectService` 의 읽기 3개(`findAll` · `findById` · `findMyProjects`)에
`@Transactional(readOnly = true)`, 쓰기 2개(`create` · `delete`)에
`@Transactional` 을 넣어 제 경계를 만든 뒤 `open-in-view: false` 로 껐다.

실측 — 경고 0건, `LazyInitializationException` 0건:

```
POST /api/projects        200  {"userId":1,"userEmail":"demo@jsp.test"}  ← LAZY 해소
GET  /api/projects        200  userEmail 정상
GET  /api/projects/2      200  userEmail 정상
GET  /api/projects/1      400  "해당 프로젝트가 없습니다" (없는 id — 의도된 응답)
```

검증용으로 만든 프로젝트는 지웠다(project 테이블 0행).

### 20. 패턴 단위 해설 — 31.8일이 사라졌다

상업화 아이디어를 묻길래 보고서 14-3 이 "해법이 필요하다" 고만 적어둔 두 지점을
실제로 재봤다. **고위험 45,075건이 서로 다른 사건인지 세어보지 않았던 것**이
드러났다.

```
Dionaea|Malware|445        22,392  (49.7%)
Suricata|Intrusion|445     18,095  (40.1%)   ← 둘 다 SMB, 합쳐 89.8%
…
전체                       45,075  →  74개 패턴
```

건별 해설은 **같은 문장을 4만 번 만드는** 일이었다. 패턴당 한 번만 부르도록
고쳐 전량 **31.8일 → 75분**, 상위 3개만 해설하면 **3분에 90%** 가 덮인다.

**🐛 그냥 재사용하면 안 됐다.** 건별 프롬프트는 IP 와 시각을 주입하고 모델은
그걸 본문에 그대로 박는다 — "2026년 5월 1일 …, 공격자 IP 203.0.113.99가 …".
그 문장을 22,391건에 나눠 쓰면 **IP 도 시각도 전부 틀린 값이 박힌다.** 화면에는
멀쩡해 보이는, 이 프로젝트가 계속 쫓아온 조용한 실패다. IP 를 키에 넣어도
(2,238그룹) 시각은 여전히 틀린다.

그래서 패턴 프롬프트에서 **IP·시각을 아예 뺐다.** 모델은 "이 허니팟·포트
조합에서 공격자가 무엇을 노리는가" 만 쓰고 사건별 값은 구조화 필드가 갖는다.
**모델이 못 본 값은 지어낼 수 없다** — 7장에서 위험도를 회수한 것과 같은 방향.

**임시 포트가 그룹을 쪼갠다.** 포트를 원값으로 쓰면 1,400그룹인데 1,287개(92%)가
1건짜리 — `Suricata|Intrusion|33414` 같은 껍데기다. 전체의 2.86% 인데 호출의
92% 를 먹는다. 접으면 74개. 처음 1024 로 접었더니 **틀렸다** — Redis(6379)·
MySQL(3306)·MongoDB(27017) 침입이 무작위 스캔과 한 해설을 쓰게 됐다. 리눅스
임시 포트 범위인 32768 을 경계로 삼아 서비스 포트는 각자 남긴다.

**실측(배치 10건 단위)**

| 배치 | 호출 | 재사용 | 비고 |
|---|---:|---:|---|
| 1차 | 7 | 3 | 캐시가 비어도 같은 배치 안에 중복이 있다 |
| 2차 | 4 | 6 | |
| 3·4차 | **0** | **10** | 배치 소요 55초 = 폴링 주기 그 자체 |
| 재기동 직후 | 1 | 9 | 색인된 패턴 해설을 찾아 쓴다 |

테스트 7건 추가(총 16) — IP·시각 누출, 임시 포트 접힘, 서비스 포트 분리를
못 박는다. `LLM_GROUP_REUSE=false` 로 되돌릴 수 있다.

> 진행 중 감시가 두 번 침묵했다. 한 번은 커서가 코퍼스 끝에 있어 처리할
> 문서가 없었던 것(`hits` 가 비면 로그 없이 반환), 한 번은 §16 과 같은
> `track_total_hits` 누락이었다. **둘 다 "침묵 = 정상 대기" 와 "침묵 = 고장"

### 23. 화면을 패턴 단위로 + 자산 노출 대조

**23-1. 🐛 파이프라인만 패턴 단위로 가고 화면이 안 따라갔다.**
llm-analyzer 가 패턴당 한 번만 해설하니 같은 문장을 가진 문서가 수백 건씩
생겼고, 건별 목록은 **똑같은 문단을 424줄 반복**하게 됐다.

백엔드에 `llmPatterns` 추가 — `llm_group_key` terms + top_hits(대표 해설) +
`src_ip` cardinality(같은 패턴을 두드린 공격자 수) + max(@timestamp).
`GET /api/exposure` 와 함께 인증 대상이다. 대시보드에 "공격 패턴" 섹션.

반복이 사라질 뿐 아니라 **측정 결과가 화면에 드러난다** — "고위험 N건이 M개
패턴이고 해설 1건이 평균 108.8건을 덮는다".

옛 건별 해설 42건은 버리지 않고 `(건별 해설)` 버킷으로 모으되, 쪼개면
"포트 -" 같은 가짜 패턴으로 보여서 화면에서 따로 표시한다.

**23-2. 🐛 임시 포트 그룹에 구체적 포트 번호가 박혔다.**
패턴 프롬프트가 대표 문서의 `dest_port` 를 그대로 넣어 모델이 "포트 44930 을
통해" 라고 썼고, 그 문장이 같은 그룹 208건에 붙어 **전부 틀린 번호**가 됐다 —
IP·시각을 뺀 것과 정확히 같은 실수를 포트에서 반복한 것이다. 임시 포트면
"임시 포트(32768 이상, 사건마다 다름)" 로 넘기고 번호를 지어내지 말라고
지시한다. 잘못된 208건은 지워 다시 만들게 했다. 테스트 2건 추가(총 18).

**23-3. 🐛 top_hits 의 _source 를 잘못 변환해 해설이 통째로 사라졌다.**
`JsonData` 를 `objectMapper.convertValue` 로 넘기면 조용히 빈 Map 이 된다.
화면에는 "분석 결과 없음" 이 아니라 **빈 칸**으로 보인다.
`h.source().to(Map.class)` 로 교체.

**23-4. 자산 노출 대조 — 보고서 14-3 의 "고객 체감 긴급성" 간극.**
허니팟 데이터는 "우리 대역을 노리는 공격" 이지 "우리가 뚫렸다" 가 아니다.
열어둔 포트를 대야 내 얘기가 된다. 파이프라인이 이미 `dest_port` 를 뽑고
있으므로 필요한 건 포트 목록뿐이다 — **ML 도 LLM 도 쓰지 않는다.**

```
⚠ 포트   445  공격 107,551  고위험 40,487  IP 228
⚠ 포트    22  공격  13,859  고위험     42  IP 582
⚠ 포트  3306  공격   1,671  고위험    248  IP 219
  포트  9999  공격     570  고위험      0  IP 131   ← 안 맞고 있다도 답이다
```

포트 목록은 **브라우저에만** 둔다(localStorage). 서버에 보관하면 "어느 조직이
어떤 포트를 열어놨는가" 를 쌓는 셈이라 조회 순간에만 넘긴다.

> 🐛 만들다 걸린 것: `src_ip` 가 ml-analysis-* 11개 인덱스 전부 **text**라
> cardinality 집계가 "all shards failed" 로 전량 실패했다. 인덱스 템플릿은
> 생성 시점에만 적용된다는, 이 프로젝트가 8-5 에 기록해둔 바로 그 함정이다.
> `src_ip.keyword` 로 집계한다.

### 25. SaaS 형태 검토 — 인증·쿼터, 자산 목록 계정화

"메인컴이 허니팟을 돌리고 이용자는 브라우저만으로" 가 되는지 확인했다.
**구조는 이미 그 모양이다** — 프론트는 허니팟을 모르고 Spring 만 부르며,
스트리밍도 이미 SSE 다. 막던 건 둘이었다.

**25-1. 🔒 `/api/analyze/*` 가 인증 없이 200 을 돌려줬다.**
본문이 그대로 프롬프트에 들어가므로 입력도 호출자가 정하고, 외부 제공자 키를
쓰는 구성이면 **남의 크레딧을 태우는 프록시**가 된다. 보고서 10장에서 Spring
쪽 `permitAll` 을 닫았는데 **Next 라우트는 같은 감사를 받지 않았다.**

**25-2. 추론이 직렬화된다(실측).** 단독 60초 · 동시 2건이면 두 번째 82초.
ollama 단일 인스턴스 CPU 추론이라 줄을 선다. 열 명이 몰리면 마지막 사람은
10분을 기다리는데 브라우저는 아무 말도 안 한다.

`lib/추론관문.ts` 로 **인증 · 쿼터(10분당 5회) · 동시 실행(2)** 을 건다.
거절된 요청은 쿼터를 소모하지 않고(혼잡으로 막힌 사람이 할당량까지 잃으면
이중 처벌), 슬롯 반납은 정상 종료·오류·**클라이언트 이탈** 모두에서 한다.

```
토큰 없음·위조 401 · 정상 200 · 동시 3건 중 세 번째 503 · 6회차 429(485초 안내)
회귀: / · /dashboard · overview · ml-stats · llm-patterns · model 전부 200
```

> 대시보드 호출부도 같이 고쳐야 했다. 토큰 없이 부르고 있어 이대로면 401 이다.
> 관문이 막으면 본문이 스트림이 아니라 JSON 이라는 점도 처리했다 — 그대로
> reader 를 열면 "분석 중" 에서 멈춘 것처럼 보인다. `res.body!` 단언도 걷었다.

**25-3. 자산 목록을 계정 단위로.** `asset_profile` 테이블 + `/api/assets`.
원문을 그대로 보관한다("웹서버 80, 443" 처럼 이름을 붙여 적으므로 포트만
뽑으면 맥락이 사라진다). 경로에 사용자 id 를 받지 않아 남의 것을 조회할
방법이 없고, 저장 시 내용을 로그에 남기지 않는다. 실측으로 다른 계정은 빈 값.

> **판단을 번복했다.** 보고서 9-6 은 "포트 목록은 서버에 두지 않는다" 고 적었다.
> 여러 사람이 한 센서를 공유하는 형태에서는 그 선택이 성립하지 않는다 — 기기를
> 바꾸면 사라진다. 민감함은 그대로이므로 **취급으로 막는 쪽**으로 바꿨고,
> 무엇이 왜 바뀌었는지 9-6 에 남겼다.

**데이터 격리가 없는 것은 이 형태에서 결함이 아니다.** `ThreatConsoleService`
는 사용자로 거르지 않고 ES 문서에 소유자 필드도 없는데, 센서가 운영자 것
하나뿐이라 모든 이용자가 같은 피드를 보는 게 정상이다. 관건은 격리가 아니라
**개인화**이고 그게 자산 대조다.

### 27. 온디맨드 추론 정책 — 이미 만들어둔 해설을 먼저 쓴다

SaaS 3단계 중 마지막. "GPU 로 올리거나 외부 API 로 돌리거나 유료 등급에만
열거나" 셋 중 고르는 문제로 봤는데, **넷째 답이 있었다.**

llm-analyzer 는 패턴당 한 번만 모델을 부르지만 결과는 **사건마다 문서로
남긴다**(§20). 그러니 고위험 사건은 대부분 **이미 해설이 있다.** 화면이 그걸
먼저 보면 추론을 부를 일이 거의 없다.

```
고위험 사건 12건 표본 · 해설 있음 12/12 (100%)
평균 42ms   vs   온디맨드 추론 60초   → 약 1,400배
```

**그룹 키를 다시 계산하지 않는다.** 임시 포트 접기 같은 규칙을 Java 에 한 번 더
옮겨 적으면 두 구현이 어긋나는 순간 조용히 틀린 해설을 보여준다(§23-2 가
그 실수였다). 대신 `source_doc_id` 로 바로 찾는다 — `llm-analysis-*` 문서의
`_id` 와 같다. `export/ml` 에 그 필드를 추가하고 목록에 실어 보낸다.

화면은 사건을 고르는 즉시 해설 카드를 띄우고, 공유 해설이면 **"이 유형 공통"**
꼬리표를 붙인다 — 사건별 맞춤 문장으로 오해하면 안 된다. "AI 분석 시작" 버튼은
해설이 이미 있으면 **"더 깊게 분석 (AI 호출)"** 로 바뀐다. 추론이 기본이 아니라
선택이 된다.

`GET /api/llm-explain?id=` (인증 필요, 없으면 `found:false`).

> 이것이 온디맨드 정책의 실질이다. GPU·외부 API·유료 등급은 **그래도 추론을
> 부를 때** 의 이야기이고, 대부분의 클릭은 애초에 추론이 필요 없다.

### 30. 🐛 프론트 LLM 경로에 한자 차단·폴백이 없었다

보고서 8장은 한자 혼입을 조용한 실패로 기록하고 고쳤다고 적었는데, **그 수정은
파이썬 사이드카에만 들어갔다.** 대시보드에서 누르는 "더 깊게 분석" 버튼은
프론트 경로(`lib/llm-service.ts`)를 쓰고 거기엔 없었다.

> ⚠️ **내 감사가 한 번 틀렸다.** 처음에 "한자·폴백·재시도·타임아웃 4개 모두
> 0건" 이라고 보고했는데, `grep -E` 에 `\|` 를 써서 리터럴 파이프로 해석된
> 탓이다. 다시 재니 **재시도(최대 2회)와 타임아웃(180초)은 이미 있었다.**
> 실제로 없던 건 한자 차단과 폴백 둘이다.

`한자포함()` 은 사이드카 `_has_cjk` 와 같은 규칙(U+4E00–U+9FFF)을 쓴다.
`JSON추출()` 이 파싱 후 한자를 확인해 **성공으로 치지 않고 재시도로 넘긴다.**

폴백은 세 자리에 넣었다:

| 자리 | 그전 | 지금 |
|---|---|---|
| `_재시도호출` | 재시도 소진 후 예외 | 폴백 결과 반환 |
| 단일 스트리밍 | `오류` 이벤트만 | 경고 + 폴백으로 대체 |
| 전체리포트 한 단계 실패 | **`return` — 리포트 전체 중단** | 경고 + 그 단계만 대체하고 계속 |
| 5단계 서술 파싱 실패 | 원문을 그대로 삽입 | 한자면 대체 |

**전체리포트가 한 단계 실패로 통째로 멈추던 게 제일 나빴다.** 그전 단계는
멀쩡하고 사용자는 이미 토큰이 흐르는 걸 봤는데, 화면이 중간에서 멈춘 채 남았다.

스트리밍은 토큰이 이미 나간 뒤라 되돌릴 수 없으므로 `경고` 이벤트를 새로 두고,
대시보드가 그걸 노란 박스로 **덧붙인다**(오류와 달리 지우지 않는다) — 사용자가
대체된 내용을 정상 결과로 읽지 않게 하는 것이 목적이다.

**테스트 6개 추가**(`frontend/tests/llm-guard.test.mjs`). node 내장 러너만
쓴다 — 빌드 산출물에 의존하면 테스트가 빌드를 먼저 요구하고, 그러면 아무도
돌리지 않는다(사이드카 테스트를 표준 라이브러리만으로 만든 것과 같은 이유).

```
한자 섞임 탐지 · 한국어/영문 통과 · 한글 기호 오탐 없음
폴백 필드 채움 · 위험등급 지어내지 않음 · 폴백 문장에도 한자 없음
→ 6/6 통과
실측: 정상 통과 · 한자 거부 · 코드 울타리 통과 · 앞뒤 잡담 통과
```

### 31. 백엔드 테스트 — 그리고 🐛 테스트가 여태 한 번도 안 돌았다

오늘 손으로 검증한 것들(격리·쿼터·401/503/429)이 전부 무보증이라 테스트를 붙였다.
그러다 **더 나쁜 것**을 찾았다.

> 🐛 **`build.gradle` 에 `useJUnitPlatform()` 이 없었다.** Gradle 이 JUnit 4
> 러너를 쓰는데 테스트는 JUnit 5 라, **하나도 찾지 못하고 BUILD SUCCESSFUL** 을
> 냈다. 테스트가 없는 것과 통과한 것이 구분되지 않았다 — 기존
> `HoneypotApplicationTests` 도 여태 실행된 적이 없다. 이 프로젝트가 계속
> 쫓아온 조용한 실패와 같은 종류이고, 하필 **테스트 자체**가 그랬다.

**테스트 22개 추가(전부 통과).**

| 파일 | 개수 | 무엇을 못 박나 |
|---|---:|---|
| `ApiExceptionHandlerTest` | 7 | 404·405·415 매핑, 내부 경로·비밀이 응답에 새지 않음 |
| `AssetProfileServiceTest` | 9 | 계정 격리, 원문 보존, 길이 상한과 경계값, 조회가 언제나 이메일로 |
| `InternalControllerTest` | 6 | **인증이 입력 검증보다 먼저**, 빠진 항목만 짚음, 빈 공유비밀이면 전부 거부 |

**Mockito 를 쓰지 않는다.** 컨테이너에서 MockMaker 플러그인이 초기화되지 않아
테스트가 대상이 아니라 자기 도구 때문에 실패했다. 리포지토리는 인터페이스라
`java.lang.reflect.Proxy` 로 필요한 메서드만 처리하는 가짜를 만들면 충분하다 —
준비물 없이 도는 사이드카 테스트와 결도 맞는다.

`InternalController` 테스트는 협력자를 **null 로** 넘긴다. 전부 토큰 검사나 입력
검증에서 끝나므로 리포지토리에 닿지 않기 때문이다. 닿으면 NPE 로 터지는데,
그건 "검증 전에 쓰기를 시도했다" 는 뜻이라 오히려 잡아야 할 신호다.

`HoneypotApplicationTests` 는 `@Disabled` 로 두고 사유를 적었다 — 전체 컨텍스트
로드에는 PostgreSQL·ES 가 필요한데, 그러면 "테스트를 돌리려면 스택부터 띄워야
한다" 가 되어 아무도 돌리지 않는다.

> 이미지 빌드는 여전히 `-x test` 다. 빌드마다 테스트를 돌리면 느려지고, 이
> 프로젝트는 사이드카 테스트도 수동 실행이 관례다. README 에 실행 명령을 적었다.

### 32. 소개 웹사이트 팀원 이름 — 역할은 붙이지 않았다

이현(팀장) · 김동현 · 홍영재 · 이재민. `promo-site/index.html` 의 `data-fill`
자리표시자 4개를 채웠다. Artifact 도 같은 URL 로 재배포(v2).

**역할 4칸(분류 파이프라인 / LLM 해설 / 백엔드·인증 / 프론트엔드)은 내가 지어낸
구분이다.** 저장소 어디에도 누가 무엇을 맡았는지가 없다. 이름만 받은 상태에서
그 4칸에 실명을 하나씩 끼우면, 그럴듯해 보이지만 **사실이 아닌 문서**가 교수와
외부에 나간다. 그래서 구조를 바꿨다 — 이름은 이름끼리(카드 4장), 맡은 일은
**팀 단위 목록**으로 따로 둔다. 어느 쪽도 거짓이 아니고, 매핑이 확정되면
`.scope` 목록을 개인별로 바꾸기만 하면 된다.

> 이건 §20 의 "패턴 단위 문장에 사건별 값을 넣지 말 것" 과 같은 종류의 문제다.
> 근거가 없는 자리에 그럴듯한 값을 채우면 검증할 수 없는 문서가 된다.

배포(`vercel deploy`)는 여전히 사람 몫이다.

### 35. 미뤄뒀던 코드 3건 — 배치 추론 · 인코더 방어 · 템플릿 이름

**35-1. `classify.py` 를 배치 추론으로.** 문서마다 `predict_proba` 를 불렀다 —
배치 1,000건이면 1,000번이다. `_classify_doc` 를 `_decide`(판단)와
`_classify_docs`(묶음 진입점)로 가르고, 특징 추출은 그대로 문서별로 하되
확률만 한 번에 구한다.

실측(실 모델 v5, 1,000건): **0.56초 → 0.02초, 23.7배.** 판단 결과는
1,000/1,000 동일했다. 실 문서 300건으로도 기존 `ml-analysis-*` 문서와 9개 필드
전부 일치를 확인했다(별도 인덱스 `ml-verify-*` 로 돌리고 지웠다).

배치로 묶으면서 **예외 범위도 배치 전체로 넓어진다**는 게 함정이다. 문서 하나가
이상해서 1,000건이 통째로 규칙 전용이 되면 그 1,000건은 `ml_label_raw` 가 비고
**화면에는 아무 경고도 안 뜬다** — 교차검증이 조용히 사라진다. 그래서
`_predict_proba_batch` 가 실패 시 행 단위로 물러서서 문제 있는 행만 버린다.

> 단위 테스트는 붙이지 않았다. `tests/run.py` 는 "준비물 없이 돈다(표준
> 라이브러리만)"가 원칙인데 `classify.py` 는 numpy·joblib 를 모듈 수준에서
> 가져온다. 그 원칙을 깨느니 실측 대조로 확인했다.

**35-2. `train.py` · `eval_vs_rule.py` 에 인코더 방어.** §4 재발 방지다.
`encoder_guard.py` 를 새로 두고 두 겹으로 본다:

1. **인코더끼리 대조** — CSV 옆 `encoders.json` 과 모델 쪽 `encoders.json`
2. **코드 범위 대조** — 인코더가 30개인데 CSV 에 코드 46이 있으면 다른 인코더다
   (옆에 `encoders.json` 이 없어도 걸린다)

§4 당시의 인코더가 그대로 남아 있어 그걸로 시험했다:

```
ERROR: 인코더가 다르다 — CSV(work-real) ≠ 모델 v4(superseded-v4)
  · event_type: 47개 vs 45개, 공통 값 중 28개가 다른 코드   → 종료코드 2
```

맞는 조합(v5)은 통과하고 99.9%/99.2% 가 그대로 나온다. `--skip-encoder-check`
로 강행하면 v4 가 **77.1%** 로 나오는데, 이게 §4 에서 봤던 그 가짜 숫자다.

**대조를 평가 전에 하는 이유:** §4 에서는 잘못된 수치가 먼저 나왔고 그게
그럴듯해서 한참을 잘못 봤다. 숫자를 보여주기 전에 막아야 한다.

**35-3. `ES_TEMPLATE_NAME` 미전달.** compose 에 `ML_ES_TEMPLATE_NAME` 으로
넘기고 `.env.example` 에 적었다. 기본값으로 충분하지만 **한 ES 에 이 스택을
두 벌 올리면 같은 이름을 서로 덮어쓴다.** 격리 실행으로 주입을 확인했다
(`index template 'ml-verify' ensured`).

검증: 사이드카 테스트 20건 통과, 이미지 재빌드 후 스택 정상, `ml-analysis-*`
11개 인덱스 1,027,047건 그대로.

### 36. 드라이브 번들을 스크립트로 — 손으로 만든 사본은 반드시 뒤처진다

§34 에서 번들을 손으로 만들었는데, 같은 날 오후 코드 3건(§35)이 들어가자마자
소스 zip 과 작업 로그가 낡았다. `make_drive_bundle.sh` 로 재생성 가능하게 했다.

```
./make_drive_bundle.sh          소스·문서·모델 갱신 (원본 로그는 재사용)
./make_drive_bundle.sh --logs   원본 로그 tar.gz 도 다시 만든다
```

판 번호를 박지 않고 `docs-versions/` 에서 최신 판을 집는다 — 새 판을 만들 때마다
스크립트를 고쳐야 하면 결국 안 고치고 낡은 판이 나간다.

**만들면서 드러난 것: 생성물 안에만 사는 파일은 재생성이 곧 소실이다.**
모델 zip 안의 `복원방법.txt` 는 그 zip 안에만 있었다. 스크립트가 폴더에서
찾으려 했고, `|| true` 가 실패를 삼켜 **새 zip 에서 조용히 빠졌다.** 파일 개수를
세보고서야 알았다. `00_README.txt` 도 같은 처지였다(`drive-upload/` 는
`.gitignore` 대상이라 폴더를 지우면 함께 사라진다).

둘 다 `bundle-assets/` 로 옮겨 저장소를 원본으로 삼고, `|| true` 를 뺐다.
`drive-upload/` 를 통째로 지웠다가 다시 만들어 확인했다 — 9개 파일 216MB,
로그 아카이브 437항목(csv 파생물 0), 소스 zip 에 `.env` 없음.

> `|| true` 로 실패를 삼키면, 없어진 것을 세보기 전까지 모른다. §16·§20 의
> "침묵과 정상이 구분되지 않는다" 와 같은 모양이다.

### 37. 감사 후속 3건 — 거짓말하는 헬스체크 · 무제한 로그인 · 백업 없음

**37-1. `/api/health` 가 아무것도 확인하지 않고 있었다.**

```java
public String health() { return "backend is running"; }   // 무조건 200
```

프로세스가 떠 있기만 하면 200 이다. **§1 에서 `dev-postgres` 가 18시간 죽어
있는 동안 이 엔드포인트는 내내 200 을 돌려주고 있었다.** 죽은 것을 살아 있다고
말하는 검사는 없는 것보다 나쁘다 — 그걸 믿고 다른 데를 뒤지게 만든다.

DataSource 는 `isValid`(풀에서 꺼낸 커넥션이 실제로 쓸 수 있는지), ES 는 `ping`
으로 두드리고, 하나라도 끊기면 **503** 을 준다. 실제로 끊어서 확인했다:

```
postgres 정지 → HTTP 503 {"status":"degraded","db":"down","elasticsearch":"ok"}
postgres 복구 → HTTP 200 {"status":"ok","db":"ok","elasticsearch":"ok"}
```

인증 없이 열린 엔드포인트이므로 **무엇이 왜 끊겼는지는 내보내지 않는다**.
상태와 짧은 이름만 주고, 예외는 서버 로그로 간다.

**헬스체크 3/11 → 7/11.** backend·frontend 는 HTTP 로, 사이드카 2종은
**heartbeat 파일**로 본다. 커서로 대신할 수 없다 — 커서는 처리할 문서가 있을
때만 움직여서 조용한 정상과 멈춤이 구분되지 않는다. §16·§20 에서 두 번 당한
그 모양이라, 할 일이 없어도 갱신되는 파일을 따로 뒀다.

> 🐛 프론트 헬스체크가 처음에 `unhealthy` 로 떴다. 서비스는 멀쩡한데
> `localhost:8001` 이 거부됐다 — 컨테이너 `/etc/hosts` 가 localhost 를 `::1`
> 로도 풀고 wget 이 IPv6 를 먼저 잡는데, `server.js` 는 `0.0.0.0`(IPv4)만
> 듣는다. `127.0.0.1` 로 바꿔 해결. 백엔드도 같은 함정을 피해 바꿨다.

**37-2. 로그인 시도 제한이 없었다.** BCrypt·JWT 는 제대로인데 비밀번호를 무한정
찍을 수 있었다. **Brute Force 2,168건 탐지를 성과로 내세우는 프로젝트의
로그인문이 무제한**이면 앞뒤가 맞지 않는다.

`LoginAttemptService` — 5회 연속 실패 시 5분 차단, 조용하면 카운터 소멸.
실측: 1~5회 400, 6회부터 429.

**IP 로 세지 않기로 한 것이 이 작업의 핵심 판단이다.** 흔한 방식이지만 이
구조에서는 쓰면 **더 나빠진다**:

- 브라우저는 Spring 을 직접 부르지 않는다. Next.js 서버 라우트가 중계하므로
  Spring 이 보는 주소는 **누가 로그인하든 프론트 컨테이너 하나**다.
  그걸로 세면 한 사람의 실패 5번이 **전원을 잠근다.**
- 프론트가 실제 IP 를 실어 보내면 되지만, **Next 15 는 `req.ip` 를 없앴고**
  브라우저가 Next 에 직접 붙어 `X-Forwarded-For` 도 없다 — 프론트 자신이
  클라이언트 IP 를 모른다.
- 백엔드가 `X-Forwarded-For` 를 믿을 수도 없다. Spring 포트(8091)가 공개돼
  있어 직접 부르며 헤더를 지어내면 그만이다. **공격자가 자기 차단을 스스로
  지울 수 있는 제한은 제한이 아니다.**

그래서 이메일 단위로만 세고, **영구 잠금이 아니라 몇 분 뒤 풀리는 차단**을 쓴다
(계정 잠금이면 남의 계정을 일부러 잠글 수 있다).

**덤으로 계정 열거를 막았다.** 로그인 실패 문구가 "존재하지 않는 이메일"과
"비밀번호가 일치하지 않습니다"로 갈려 있었다 — 응답만 보고 **어떤 이메일이
가입돼 있는지 알 수 있다.** 하나로 합쳤다.

> ⚠️ 남은 구멍: `/api/users/check-email` 은 여전히 가입 여부를 그대로 알려준다
> (회원가입 폼이 쓴다). 위 통합의 효과를 상당 부분 상쇄한다. 프록시 구조상
> IP 별 제한이 안 되므로 전역 상한밖에 못 거는데, 그건 **공격자가 회원가입을
> 막는 DoS 로 쓸 수 있다.** 어느 쪽을 택할지는 판단이 필요해 남겨둔다.

**37-3. Postgres 백업이 없었다.** 계정·자산 목록이 볼륨에만 있고 `down -v`

### 39. 번들이 계속 낡는 문제 — 재생성이 아니라 감지를 자동화했다

§36 에서 스크립트로 만들었는데도 두 번 더 낡았다. 둘 다 같은 모양이다:
코드를 고치고, 커밋하고, **번들 갱신을 잊는다.**

재생성을 자동화(커밋 훅에서 매번 실행)하는 쪽을 먼저 생각했는데, 재보니 **70초**
다. 커밋마다 70초를 쓰면 곧 거슬려서 훅을 지우게 되고 원래 문제로 돌아온다.
그래서 **알리기만 한다**:

- `drive-upload/MANIFEST.txt` — 이 번들이 **어느 커밋 기준인지** 적는다.
  폴더만 봐서는 최신인지 알 길이 없었고, 낡은 채로 올리는 사고가 그렇게 난다.
  드라이브를 받은 팀원도 이 파일로 확인할 수 있다.
- `--check` — 1초. 기록된 HEAD 와 현재 HEAD 를 비교하고, 뒤처진 커밋을 보여준다.
  커밋은 같아도 **커밋 안 된 변경**이 있으면 그것도 알린다(그 변경은 `git archive`
  에 담기지 않는다).
- `--install-hook` — `post-commit` 에서 `--check` 를 돌린다. 재생성은 안 한다.

설치 직후 커밋에서 바로 걸렸다:

```
드라이브 번들이 낡았습니다. 올리기 전에: T-POT_PR/make_drive_bundle.sh
```

> **남은 구간:** 디스크가 최신이어도 드라이브가 최신이라는 보장은 없다. 업로드가
> 손이라서다. 없애려면 Drive 데스크톱 앱의 동기화 폴더로 번들을 만들거나
> (rclone 으로 `--push` 를 붙이거나) 해야 하는데, 둘 다 사용자 구글 로그인이
> 필요해 사람이 한 번 해줘야 한다. MANIFEST 가 있어 **받은 쪽에서도 낡았는지는
> 알 수 있다** — 모르고 쓰는 것보다는 낫다.

### 1. 🔒 위협 데이터 전체가 인증 없이 열려 있었다

`SecurityConfig` 에서 threat-console 흡수분이 전부 `permitAll` 이었다.

```
토큰 없이 GET /api/llm-recent  →  200
{"src_ip":"203.0.113.99","honeypot":"Cowrie","ml_label":"Intrusion",
 "mitre_score":85,"summary_ko":"...공격자 IP 203.0.113.99가 SSH 포트(22)를..."}
```

공격자 IP·허니팟·한국어 위협 분석 전문이 그대로 나왔고, `/api/export/**` 는
전체를 CSV 로 내려줬다. **화면에는 로그인 관문이 있었지만 데이터는 그 뒤에 있지

`.authenticated()` 로 옮겼다. 닫아도 안전한 근거를 먼저 확인했다:
프론트 프록시는 이미 `Authorization` 을 전달하고(`인증전달(req)`),
독립형 threat-console 은 Spring 이 아니라 **ES 를 직접** 읽는다.

실측: 토큰 없이 403 · 토큰 있으면 200 · `/api/health` 는 공개 유지 ·

**pytest 를 쓰지 않았다.** 사이드카 이미지에도 팀원 PC 에도 없다.
테스트를 돌리는 데 준비물이 필요하면 아무도 안 돌린다 — 표준 라이브러리만 쓰는
`tests/run.py` 를 직접 만들었다.

테스트는 "함수가 도는가"가 아니라 **겪은 실패를 하나씩** 못 박는다:
`int("23.0")`→포트 0, suricata `payload` 미조회, 경보 없는 행→정찰,
`network-scan`→침입, `severity==2`→악성코드, LLM 이 고위험에 `LOW` 반환,
한자 혼입, 폴백 필드 누락, 코드 울타리 섞인 JSON.

### 5. 🐛 테스트가 곧바로 실제 공백을 잡아냈다

첫 실행에서 1건 실패 — **파이썬 리버스셸이 탐지되지 않았다.**

```
REVERSE_SHELL_KEYS = ("bash -i", "/dev/tcp", "nc -e", "mkfifo", "ncat")
python -c 'import socket,os,pty;s=socket.socket()'   → Recon (침입이어야 함)
```

wget/curl 도 `/dev/tcp` 도 없어 cowrie 분기 마지막 줄로 떨어졌다.
**침입이 정찰로 기록되는 것**이고, `mitre_score` 도 낮게 매겨져 LLM 게이트(≥70)를
통과하지 못하므로 한국어 해설조차 안 만들어진다.

정규식을 보탰다(python/perl/ruby/php + socket, socat, `nc -e`, `telnet | sh`).
전부 **조합**을 요구한다 — `socket` 낱말 하나로 걸리면 평범한 조회가 침입이 된다.
오탐 테스트를 같이 넣었다(`ls -la`, `cat /etc/passwd`, `python -c 'print(1+1)'`,
`netstat -an | grep socket` → 전부 Recon 유지).

**판단을 한 함수로 모았다.** 세 군데(공통 판정·cowrie 분기·기본 폴백)가 각자
목록을 훑고 있어서, 규칙을 고치면 **허니팟에 따라 답이 갈렸다.**
`_is_reverse_shell()` 하나로 통일하고, 같은 명령이 cowrie·honeytrap·snare·미지
허니팟에서 모두 같게 나오는지 테스트로 고정했다.

**수치 영향 없음(확인함).** 현재 1,736건에 이 패턴이 0건이라 라벨 분포가

### 2. 🐛 `ml-classifier` 인덱스 템플릿 부재

폼보드 수치를 검증하다 발견했다. **분류기에는 인덱스 템플릿이 아예 없었다** — 모든 필드가
동적 매핑이다. 지금까지 안 터진 것은 소비자가 우연히 `model_used.keyword` 처럼 하위필드를
쓰고 있었기 때문이지 설계가 안전해서가 아니었다. `llm-analyzer` 에 이미 넣어둔 것과 같은
구멍이 `ml-analysis-*` 에 그대로 남아 있었다.

`ml-analysis-*` 는 **하루에 하나씩 새 인덱스**가 생기므로, 템플릿이 없으면 "그날 처음 들어온
문서" 모양대로 타입이 잡혀 `ml-analysis-*` 조회가 **날짜별로 갈릴 수 있다.**

**설계 판단 — 타입을 "더 좋은 것"으로 올리지 않았다.** `src_ip`→`ip`, `mitre_score`→`integer`
로 올리면 오늘 인덱스는 `text`, 내일 인덱스는 `ip` 가 되어 오히려 갈린다. 템플릿은
**지금 인덱스에 있는 모양 그대로** 고정하는 데 썼다. 타입을 올리려면 전체 reindex 가 함께 가야 한다.
소비자가 `.keyword` 하위필드로 집계하므로 `ml_label`·`honeypot`·`model_used` 는 text+keyword
형태를 유지해야 한다 — 바로 `keyword` 로 바꾸면 하위필드가 사라져 집계가 깨진다.

실측 확인: `dest_port` 에 `"23.0"` → 숫자 23 으로 강제변환 색인(`_source` 엔 원문 유지),
`"abc"` → `document_parsing_exception` 으로 거부·로그. 어느 쪽이든 필드가 `text` 로 굳어
집계가 죽는 일은 없다. 기존 인덱스에도 `_ensure_field_mappings()` 로 밀어 넣었고 **충돌 0건** —
"있는 모양 그대로" 설계가 맞았다는 확인이다.

### 8. 백엔드 — 보안 결함 1건 + 데이터 정합성 1건

**🔴 JWT 서명 키가 소스에 하드코딩** (`JwtUtil.java`)
```java
private final String SECRET = "my-secret-key-my-secret-key-my-secret-key";
```
저장소를 볼 수 있는 누구나 **임의 사용자의 토큰을 위조**할 수 있었다. 환경변수 `JWT_SECRET` 로 옮기고, 미설정 시 기동할 때 임의 키를 만들되 경고를 남긴다(재기동하면 토큰 무효 — 운영에선 반드시 설정하라는 신호). base64/평문 both 허용, 32바이트 미만이면 기동 실패. 만료도 `JWT_EXPIRATION_MINUTES` 로 설정 가능하게.
검증: 토큰 있음 → `/api/users/me` 200, 없음 → 403.

**🔴 실패가 그럴듯한 가짜 분석으로 둔갑** (`AnalysisService` → `AttackLogService`)
외부 FastAPI 호출이 실패하면 `riskScore 50 / MEDIUM / "자동 분석 실패..."` 를 만들어 돌려줬고, 호출부가 그것을 **그대로 DB 에 저장**했다. 화면에서는 진짜 분석과 구분되지 않는다. 게다가 compose 는 `FASTAPI_URL: http://disabled.local:8000` — 존재하지 않는 호스트라 적재할 때마다 DNS 를 두드렸다.
- `Optional` 반환으로 바꿔 **실패하면 분석 결과를 남기지 않는다**(`analysis: null`).
- 기본 `RestTemplate` 은 **타임아웃이 없다** — 상대가 멈추면 서블릿 스레드가 무한 대기하고 적재 API 전체가 같이 멎는다. connect 2초 / read 5초 지정하고 빌더로 재사용.
- 외부 서비스를 **선택 구성**으로 명시(`FASTAPI_ENABLED=false`). 미구성이 정상 상태다 — 주 분석 경로는 ES 사이드카다.
- `(Integer) result.get("riskScore")` 는 JSON 이 Double 로 오면 ClassCastException 이다. `Number#intValue` 로 안전하게.

검증: 적재 **74ms** 성공, `analysis: null` 로 정직하게 저장. 기동 로그에 "외부 분석 서비스가 구성되지 않았습니다" 안내.

### 9. 백엔드 마무리 — 결함 4건 추가

**🔴 모든 오류가 403 으로 뭉개짐**
서비스가 던진 `IllegalArgumentException` 이 컨테이너까지 올라가 Spring 의 `/error` 로 포워딩되는데, 그 경로가 인증 대상이라 **403 Forbidden** 이 나갔다. "이미 사용 중인 이메일입니다" 같은 메시지가 클라이언트에 전혀 도달하지 못했다.
→ `ApiExceptionHandler`(`@RestControllerAdvice`) 신설: IllegalArgument→400, NoSuchElement→404, 그 외→500(내부 사정은 로그에만). `/error` 도 permitAll 에 추가.
검증: 중복 이메일 `403` → **`400 {"message":"이미 사용 중인 이메일입니다."}`**

**🔴 N+1 쿼리** (`AttackLogService.findLogsWithAnalysisByProject`)
로그를 전부 가져온 뒤 **건별로** 분석 결과를 다시 조회했다. 로그 1,000건이면 쿼리 1,001번.
→ `findByAttackLogIdIn` 배치 조회 + 메모리 매핑으로 **쿼리 2회 고정**.

**🔴 로그인·회원가입이 백엔드를 호출하지 않음**
가장 큰 기능 결함이었다. 백엔드 인증(JWT)은 완전히 동작하는데 **프론트가 전혀 쓰지 않았다.**
- 회원가입: `setTimeout(1200)` 으로 성공을 흉내 내고 로그인 화면으로 보냈다. **계정이 만들어지지 않아 곧바로 로그인 실패.**
- 로그인: 하드코딩된 `ACCOUNTS = { admin: "admin123", user1: "user1234" }` 로 프론트에서 판정. 비밀번호가 브라우저에 노출됐고 실제 계정과 무관했다.
→ `/api/auth/[action]` 서버 라우트 신설(백엔드 주소 은닉 + 10초 타임아웃), 두 화면을 실제 API 에 연결. 로그인 성공 시 JWT 를 `localStorage` 에 저장.
검증(프론트 경유): 중복 가입 400·한국어 메시지 / 신규 가입 200 / 로그인 토큰 발급 / 틀린 비번 400.

**문구·색 잔재**
존재하지 않는 계정을 안내하던 `admin / admin123` 배너 제거, "무료 회원가입/무료 가입" 등 SaaS 문구 정리, `globals.css` 에 남아 있던 보라 그라데이션 2곳을 강조색으로 교체.

### 10. 대시보드 인증 연결 — 토큰이 실제로 쓰이게

§9 에서 로그인이 토큰을 받아오게는 했지만 **대시보드가 그것을 쓰지 않았다.** 누구나 `/dashboard` 를 열 수 있었고 프로젝트 권한 분리도 의미가 없었다.

- `src/lib/auth.ts` 신설 — 토큰 보관/삭제, `인증fetch`(401·403 이면 토큰 폐기). localStorage 접근은 사생활 보호 모드에서 예외를 던지므로 전부 try/catch (저장 실패와 앱이 죽는 것은 다르다).
- `/api/auth/me` 라우트 — **토큰의 존재가 아니라 유효성**을 서버에 물어본다. 만료됐거나 서명 키가 바뀌면 무효인데 localStorage 값은 그대로 남기 때문이다.
- 대시보드 진입 시 로그인 확인 → 없거나 무효면 `/login` 으로. 헤더에 로그인 이메일과 로그아웃 버튼 추가.
- `/api/overview`·`/api/attacks` 가 `Authorization` 을 백엔드로 전달. 지금 이 엔드포인트들은 permitAll 이지만(순정 T-Pot 배포에서도 쓰인다) 권한을 조여도 화면이 그대로 동작한다.

검증: 토큰 없음 → `/api/auth/me` 401 · 대시보드가 로그인으로 리다이렉트 / 위조 토큰 → 401 "로그인이 만료되었습니다" / 정상 토큰 → `{"email":"demo@jsp.test"}` + 데이터 조회 정상.

### 11. ML — 라벨러 개선 후 재학습

천장의 원인이 "모델"이 아니라 "라벨"에 있었으므로 `rule_label.py` 를 고쳤다.
**규칙은 학습 정답이자 동시에 운영 분류기다** — 여기를 고치면 양쪽이 같이 좋아진다.

**고친 것 4가지**
1. **suricata 가 payload 를 전혀 안 봤다** — `alert.category` 와 severity 만 썼다. 페이로드에 `bash -i >& /dev/tcp/...` 가 있어도 카테고리가 `attempted-recon` 이면 Recon 이 됐다. 내용에 확실한 근거(리버스셸·원격 실행파일 다운로드)가 있으면 **카테고리보다 우선**하도록 바꿨다.
2. **`network-scan` 이 INTRUSION 목록에도 있었다** — INTRUSION 을 먼저 검사하므로 네트워크 스캔이 전부 침입으로 분류됐고, RECON 쪽 항목은 죽은 코드였다.
3. **`severity == 2 → Malware`** — 멀웨어라는 신호가 어디에도 없는데 그렇게 불렀다. 제거.
4. **경보 없는 suricata 행을 Recon 으로 불렀다** — suricata 는 flow·dns·tls 같은 자체 기록도 남기는데 그런 행엔 카테고리도 심각도도 없다. **실측 20만 행 중 146,441행(73%).** 공격 근거가 0인 행을 "정찰"이라 부르면 그 라벨의 정의가 무너진다 → `Etc`(무해/불명).

또 `rule_label` 의 텍스트 추출을 `_text_of()` 로 통일해 `payload_printable` 을 포함시켰다(기존엔 input/command/message 세 개만 봤다). honeytrap·tanner 도 원격 다운로드를 잡는다.

**코퍼스 609,252행 변화 (규칙 개선 전 → 후)**

| 라벨 | 전 | 후 | 변화 |
|---|---:|---:|---:|
| Recon | 518,130 | 406,311 | **−111,819** |
| Etc | 844 | 147,285 | **+146,441** |
| Malware | 58,698 | 23,793 | −34,905 |

| Brute Force | 23,062 | 23,062 | 0 |

라벨이 바뀐 행 **181,759건(29.8%)**. 가장 중요한 지표:
**리버스셸 페이로드인데 Intrusion 이 아니던 행 322/384 → 0/384.**
특징과 라벨이 서로를 부정하던 문제가 사라졌다.

**재학습 결과 (실제 ES 문서 300건 기준)**

| 모델 | 일치율 | 주요 오류 |
|---|---:|---|
| v2 조인 전 | 15.7% | BruteForce→Recon 130 |
| v3 세션 조인 | 59.0% | Intrusion→Malware 63 · Malware→Recon 60 |
| **v5 라벨 개선** | **79.0%** | Intrusion→Malware 63 |
| v6 +희소신호 보존 | 79.0% | 동일 |

`rebalance.py` 에 **희소 신호 보존**을 추가했다(결정적 특징을 가진 행은 무작위 트리밍에서 제외). 리버스셸 행이 61 → 854 로 늘었지만 일치율은 그대로였다.

**남은 오류 63건의 정체 — 데이터 커버리지**
전부 cowrie 리버스셸 문서다. 진단해보니 **리버스셸 384행이 전부 suricata 이고 cowrie 에는 0건**이다(원본 `cowrie.csv` 에 리버스셸 명령이 실제로 없다). 모델은 `cowrie + revshell` 조합을 본 적이 없어 가장 가까운 `cowrie + wget → Malware` 로 답한다.
평가에 쓴 "실제 ES 문서"가 사실은 **주입한 합성 샘플**이고, 거기 포함된 시나리오가 실제 수집 데이터엔 없다. 이 간극을 학습 데이터를 합성해 메우면 **자기 시험지를 베끼는 것**이 되므로 하지 않았다.

**ML 활성화 여부: 여전히 비활성**
라벨이 규칙에서 파생되는 한 모델의 천장은 규칙 재현(100%)이고 현재 79%다. 다만 이번 작업의 실익은 모델이 아니라 **규칙 자체가 좋아진 것**이다 — 규칙이 운영 분류기이므로 그대로 서비스 품질 향상이다.

**데모 데이터에서는 변화가 안 보인다** — 재분류 결과가 개선 전후 거의 동일하다(Brute Force 654→655 등). 주입 샘플이 cowrie/conpot/heralding 뿐이고 **suricata 문서가 하나도 없어서**, 개선이 겨냥한 대상이 데모 데이터에 존재하지 않는다.

**함께 고친 것**: `BOOTSTRAP_WINDOW` 를 compose 로 설정 가능하게 했다(기본 `now-5m` 이라 커서를 지우고 재분류해도 5분 이전 문서를 전혀 못 봤다 → dev 는 `now-24h`).

### 12. ML 활성화 — 규칙을 대체하지 않고 교차검증으로

**🐛 먼저 고친 위험한 결함** (`classify.py`)
모델이 있으면 라벨을 통째로 덮어썼고, 신뢰도가 임계값 미만이면 `"Normal"`(무해)로 바꿨다.
**모델이 처음 보는 공격일수록 무해로 표시되어 고위험 파이프라인에서 사라진다** —
보안 도구가 가면 안 되는 방향이다.

**새 설계: 규칙이 기준선, 모델은 교차검증**

| model_used | 의미 |
|---|---|
| `ml+rule` | 모델·규칙 합의 → 신뢰도 높은 건 |
| `rule(dissent)` | 모델이 다른 답 → **검토 대상**(라벨은 규칙을 따름) |
| `rule(low-conf)` | 모델이 확신 못 함 → 규칙 |
| `rule` | 모델 없음/실패 |

모델은 라벨을 **뒤집지 못하고** 대신 신뢰도(`ml_multi_conf`)와 원 판단(`ml_label_raw`),
불일치 플래그(`ml_dissent`)를 남긴다.

**실측 (신규 100건)**: 합의 85 · 불일치 15 · 저신뢰 0 → **합의율 85%**, 합의 건 신뢰도 평균 99.9%.
불일치 15건은 **전부 `규칙 Intrusion vs 모델 Recon`** — §11 에서 진단한 cowrie 리버스셸
학습 공백과 정확히 일치한다. 규칙이 이겨 라벨은 옳고, 모델은 자기가 모르는 영역을 정직하게 드러냈다.

**대시보드 반영**: `/api/ml-stats` 신설로 **실제 합의율**을 모델 카드에 표시한다.
holdout 99.94% 는 정답 라벨을 규칙에서 뽑아 부풀려진 값이라 맥락 없이 띄우면 화면이 거짓말한다.
운영에서 의미 있는 숫자는 "지금 들어오는 문서에 대해 모델이 규칙과 얼마나 합의하는가"다.

### 3. LLM severity — 모델에서 회수
`eval_severity.py` 신규로 먼저 측정(qwen2.5:3b, 고위험 10건): `current` raw_low **10/10**, `fewshot` raw_low **10/10**. **판정 예시를 넣어도 전혀 안 바뀜 → 프롬프트가 아니라 능력 한계.**
- `LLM_SEVERITY=derive`(기본): severity/risk를 아예 묻지 않고 `mitre_score`에서 유도. 모델은 잘하는 것(요약·대응방안·TTP)만 담당. 프롬프트도 짧아짐
- `LLM_SEVERITY=model`로 더 강한 모델에 판정을 되돌려줄 수 있음(하한 가드는 유지 — 올릴 수는 있어도 내릴 수 없음)
- `severity_adjusted`(항상 true라 무의미) → **`severity_source`**(`score`|`llm`|`raised`)로 교체
- **🐛 템플릿 사각지대:** 인덱스 템플릿은 *생성 시점*에만 적용된다. `severity_source` 추가 시 기존 인덱스에 동적 매핑으로 `text`가 붙어 집계가 조용히 실패 — 8/25에 템플릿으로 막았던 그 실패가 재발. `_ensure_field_mappings()`로 기동 시 기존 인덱스에도 필드 push, 타입 충돌은 숨기지 않고 경고+reindex 안내

### 3. 🐛 재학습 ML 모델 비활성화 — 룰보다 나빴음 (실측)
문서상 "다음 작업 1순위"였던 모델 배치(`dataset/work/models/` → `MODEL_DIR`)를 수행했으나, **주입 샘플 60건이 전부 `Recon`(신뢰도 96~99%)** 으로 분류됨. `mitre_score`가 32에 머물러 **고위험 0건 → llm-analyzer가 아무 일도 못 함**.

원인을 `balanced.csv`에서 실측:
- `event_type=24`(cowrie.login.failed) 행은 **269건 전부 Brute Force**
- 그러나 `Brute Force` 클래스 10,000건 중 **9,110건이 source_honeypot=15**, **9,710건이 event_type 공백**
- cowrie(=2) 행 2,285건은 **Recon 1,994 / Brute Force 290**

→ 모델이 학습한 건 "Brute Force = honeypot 15 + 빈 event_type"이지 "cowrie.login.failed = Brute Force"가 아님. cowrie가 보이면 다수 클래스 Recon으로 눌러버림. **피처 순서·인코더 어휘는 학습 CSV와 정확히 일치함을 확인했으므로 배선 버그가 아니라 라벨 품질/클래스 편중 문제** (기존 기록 "0.998은 과대평가"와 일치).

**대조 — 같은 문서, 룰 기반은 4종 전부 정확**: cowrie.login.failed→Brute Force(65) / ConPot 스캔→Recon(32) / `wget x.sh`→Malware(92) / `bash -i >& /dev/tcp/`→Intrusion(85).

→ 모델을 `models/disabled-recon-biased/`로 **보존 이동** + `WHY_DISABLED.md`에 근거·복구 절차 기록. 사이드카는 모델이 없으면 자동으로 룰 폴백(`model_used: rule`). **되돌리려면 두 파일을 `models/` 최상위로 옮기고 재시작.**

### 4. llm-analyzer 실모델 검증 + 🐛 severity 가드 추가
- **8B는 OOM** — `llama3.1:8b`(4.9GB)은 호스트 RAM 7.8GB에서 `llama-server terminated: signal killed`. → **`qwen2.5:3b`(1.9GB)** 로 교체(한국어 품질 고려). `.env`에 고정.
- **실모델 최초 성공**: 24건 `analysed=24, indexed=24, errors=0, fallback=0`. CPU 추론 ~27초/건.
- **🐛 발견 — severity가 mitre_score와 정면 모순**: `mitre_score` 85·92 문서에 모델이 `severity: LOW`, `risk_score: 3.0`을 반환. 대시보드에 고위험을 LOW로 표시하는 건 적극적으로 위험. 파이프라인이 이미 `>=70`만 통과시키므로 **내부 모순**.
- **수정**: `parse_response`에 결정론적 **하한선 가드** — LLM은 점수 기준 severity보다 **올릴 수는 있어도 내릴 수는 없음**. `risk_score`도 severity와 모순되지 않게 하한 적용. 프롬프트에 점수 구간 명시 + "한국어만, 한자 금지"(qwen이 `악意大용` 같은 중국어 토큰 누출) 추가.
- **`severity_adjusted` 계측 필드 신설** → 결과: **24/24 전부 보정됨**. 즉 qwen2.5:3b는 severity 판단을 **단 한 건도 못 맞춤**; 현재 대시보드의 severity 정확성은 전적으로 이 가드가 담보하고 있음. 이 비율이 모델 교체 판단 지표.

### 5. 기동 중 발생/해결한 이슈

1. **suricata/fatt OCI mount 에러** (Docker Desktop WSL2 바인드마운트 캐싱 버그): tpotinit이 데이터 디렉토리 만들기 전에 컨테이너 시작 시도. `docker rm -f <stuck>` 후 `up -d` 재실행으로 해결 (5/7 노트의 기존 알려진 패턴).
2. **사이드카 PermissionError**: `/data/ml-classifier`, `/data/threat-console`는 tpotinit이 모르는 디렉토리. Docker가 자동 mkdir 시 root 소유로 만듦 → 컨테이너 uid 2000 권한 거부.
   - 해결: `docker exec tpotinit chown -R 2000:2000 /data/ml-classifier /data/threat-console` + chmod u+rwX,g+rwX + 사이드카 restart.
   - **재발 가능성**: 데이터 디렉토리 통째 삭제 후 재기동 시 같은 문제 재현. infra_only.yml에 init container 추가하거나 사이드카 Dockerfile에서 USER 변경 검토 필요.
3. **nginx HTTP 500 (`pread() nginxpasswd failed: Is a directory`)** — 5/7 노트의 알려진 이슈 재현. tpotinit이 `.env`의 base64 WEB_USER를 디코딩해 `/data/nginx/conf/nginxpasswd` 파일에 써야 하는데 빈 path 탐지 후 디렉토리로 mkdir해버림.
   - 해결: `docker exec tpotinit sh -c 'rm -rf /data/nginx/conf/nginxpasswd && echo "<WEB_USER_BASE64>" | base64 -d > /data/nginx/conf/nginxpasswd && chmod 644 ...'` 후 nginx 컨테이너 **rm + recreate** (단순 restart는 마운트 캐싱 버그로 실패 — inode 잔존).
   - 검증: `curl -ksI https://IP:64297/` → 401 (basic auth challenge), `-u admin:admin` → 200, `/kibana/` → 302, `/threat-console/` → 200.
